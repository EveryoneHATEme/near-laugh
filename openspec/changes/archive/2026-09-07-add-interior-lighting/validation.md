## Measurement method

`interior_lighting_measure` is an explicit, excluded-from-default-build
development target. It uses the ordinary Engine tick, with neutral sampled
input for stationary views or concrete waypoint/input sequences for the route.
It records 10 seconds warm-up followed by 60 seconds, retains raw rows in
bounded memory, then writes CSV after renderer teardown drains pending queries.
`check` is a short correctness run with presentation recovery, not a benchmark.

CPU active work is tick/driver elapsed time minus separately measured fence,
acquire and present calls. Frame intervals are successive CPU frame completion
intervals, not measured display scanout latency. GPU timestamps bracket command
buffer work after the acquisition semaphore. Query results use the selected
graphics queue's valid bits and device timestamp period, and are read only
after the slot fence or successful device-idle teardown. Missing GPU results
remain empty CSV fields, never inferred from CPU intervals. Shadow work is
explicitly zero in the current unshadowed baseline.

API references: [timestamp writes](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdWriteTimestamp2.html)
and [query availability/readback](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetQueryPoolResults.html).

## Saved-file Play acceptance

The actual Debug editor was launched from the separate working directory
`D:/programming/near-laugh/build/проверка P10` with the packaged six-light
scene. File > Save As wrote `освещение.level.json` in that directory. In the
Properties panel, disabling `room-ceiling.initially_on` made the document
dirty; Play opened the Save and Play modal. Confirming saved v8 with that

The game displayed the dark initial room and closed normally with code 0.
Undo restored the initial flag; another Save and Play launched a fresh process
with the room light enabled. It also closed with code 0. The final saved
document equals the packaged scene. The original source file was unchanged.

Screenshots and the final saved snapshot are in `captures/editor-play`.
These ordinary UI/game windows are 1600x900/1024x768; the quantitative GPU
readbacks and performance runs use their separately checked 1920x1080 modes.

the editor refused that save and retained the usable document. Correcting the
helper to `PostMessageW` allowed Unicode Save As without restarting the editor.
No product code was changed for that input-helper defect.

## Launch-environment pacing investigation

The initial PowerShell batch (`measurements/final`) was launched through the
agent's default isolated execution environment. Its three six-light stationary
samples had poor frame pacing despite GPU work fitting the budget. For example,
sample 2 measured GPU p95=12.22964 ms, CPU p95=0.7203 ms, frame
p50/p95/p99=31.5730/46.3025/46.7765 ms and acquisition
p50/p95/p99=30.9800/45.6730/46.1161 ms. The subsequent route was deliberately
closed before warm-up completed to investigate; its partial CSV is not a sample.

Direct executable invocations restored ordinary pacing with no binary, shader,
scene, display-mode or power-plan change. `pacing-direct-control.csv` measured
GPU p95=10.49212 ms and frame p50/p95/p99=16.6735/17.3900/17.6709 ms;
`pacing-direct-capacity.csv` passed all gates with GPU p95=11.19392 ms.
Disabling only the two existing OW implicit layers for a controlled wrapper
run (`pacing-wrapper-no-overlay.csv`) did not resolve the delay: frame
p50/p95/p99=31.6556/46.2269/46.6545 ms. The environment variable was removed
after that run. There is no evidence identifying either layer as the cause.

The identical batch script was then launched explicitly on the ordinary Windows
desktop, outside the agent's isolated execution environment. The first sample
in `measurements/desktop-final` passed all gates: GPU p95=10.54388 ms and frame
p50/p95/p99=16.6816/17.3590/17.6606 ms. This reproduces the direct-launch
behavior and identifies the launch environment as a measurement condition;
it does not identify an OS/driver mechanism. Final acceptance repetitions use
this ordinary-desktop invocation. All failed raw runs are retained separately,
including the original unshadowed baseline outlier with similar acquisition
delays. No renderer scheduling change was made in response to these delays.
